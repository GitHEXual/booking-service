# Сервис записи на встречи с видеоконференцией

Аналог Calendly: эксперт задаёт виды встреч и часы приёма, гость открывает
публичную ссылку, видит свободные слоты и отправляет заявку. Один слот это один
гость. Сразу после заявки в Телемосте создаётся встреча, организатор получает
письмо со ссылкой, а гость получает ссылку перед началом.

## Как устроен продукт

**Один слот это один гость.** Второй записавшийся на то же время получает отказ.
Правило держит частичный уникальный индекс, поэтому оно работает и при
одновременных запросах.

**Встреча создаётся сразу после заявки.** Фоновый воркер создаёт её в Телемосте
токеном эксперта и кладёт организатору письмо с данными гостя и ссылкой. Гость
получает письмо со ссылкой перед началом.

**Панель показывает ближайшие встречи.** На главной видно, кто и когда
записался, есть кнопка подключения и удаление слота. Удалить можно и вид встречи
целиком.

## Решения, которые приняты

- Стек: FastAPI, React 19 и Vite, PostgreSQL, SQLAlchemy 2.0 async, Alembic.
- Эксперт входит через OAuth Яндекс ID. Гость не регистрируется.
- Слоты вычисляются из недельного расписания и не хранятся.
- Один слот это один гость; время освобождается после удаления заявки.
- Встреча создаётся в Телемосте сразу после заявки, письмо организатору уходит
  тогда же.
- Письма: организатору про заявку со ссылкой, гостю напоминание перед началом.
- Персональные данные шифруются на уровне колонок, поиск идёт по слепому
  индексу.

## Что ещё не решено

| Вопрос | Почему это важно |
|---|---|
| Права Телемоста в приложении | Проверь, что приложению доступны `telemost-api:conferences.create`. Список прав приложения отдаёт `https://oauth.yandex.ru/client/<client_id>/info`. Пока их нет, `YANDEX_OPTIONAL_SCOPE` пуст: иначе Яндекс отменяет всю авторизацию |
| DNS-записи отправляющего домена | SPF, DKIM и DMARC. Без них письма уходят в спам, хотя SMTP отвечает успехом. Для разработки на личном ящике можно не делать |
| Где размещается сервис | Требование говорит об облачном хостинге, конкретная площадка не выбрана |
| Синхронизация с внешними календарями | Без неё занятость знает только сервис. Осознанное ограничение, зафиксированное в PDR |

## Настройка

```bash
cp .env.example .env
```

В `.env` ключи для локальной разработки уже сгенерированы. Остаётся вписать
`YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`, а также `SMTP_USERNAME` и
`SMTP_PASSWORD`. Формат каждой переменной и место, где её взять, описаны в
`.env.example`.

Отправка через SMTP проверена: подключение к `smtp.yandex.ru:465` и авторизация
с паролем приложения работают.

## Что нужно поставить

- Python 3.14
- Node.js 22 или новее
- Docker с Docker Compose

## Запуск

Сервис и база:

```bash
docker compose up -d --build
```

Интерфейс, в отдельном терминале:

```bash
cd frontend
npm install
npm run dev
```

Панель открывается на http://localhost:5173. Запросы к `/api` и `/auth`
Vite отправляет сервису на порт 8000, поэтому второй порт в адресах не
участвует.

Миграции накатываются отдельно, перед первым входом:

```bash
docker compose exec api alembic upgrade head
```

## Тесты

```bash
docker compose run --rm api pytest
docker compose run --rm api ruff check .
cd frontend && npm run typecheck
```

Тесты идут против настоящего PostgreSQL из docker compose, а не против SQLite:
в моделях есть то, что на SQLite не заработает, и подменять хранилище значило бы
проверять не то, что пойдёт в бой.

## Что уже сделано

1. Каркас: `pyproject.toml`, Docker Compose с PostgreSQL, настройки, ключи
   шифрования.
2. Схема и миграции Alembic, частичный индекс на активную заявку (ADR 0004).
3. Слоты как чистые функции и тесты на них.
4. Вход эксперта через Яндекс ID.
5. Гостевая часть: страница вида встречи, сетка слотов, заявка.
6. Воркер: встреча в Телемосте сразу после заявки и письмо организатору.
7. Напоминание гостю перед началом.
8. Панель эксперта: главная с ближайшими встречами, удаление слота и встречи.

## Непрерывная интеграция

Проверки описаны в `.github/workflows/ci.yml` и запускаются на каждый push в
`main` и на pull request. GitHub подхватывает только то, что лежит в
`.github/workflows`, поэтому без этого файла тесты сами не запускаются.

Что делает CI:

- поднимает PostgreSQL как сервис;
- ставит Python 3.14 и зависимости, гоняет `ruff check .` и `pytest`;
- ставит Node.js 22, проверяет типы и собирает интерфейс;
- отдельной задачей собирает Docker-образ.

## Релизы и доставка

`.github/workflows/release.yml` запускается по тегу вида `v1.2.3`. Он собирает
образ, публикует его в GitHub Container Registry и создаёт GitHub Release со
списком изменений. Тег ставит человек:

```bash
git tag -a v1.0.0 -m "Первый релиз"
git push origin v1.0.0
```

Образ ложится в `ghcr.io/<владелец>/<репозиторий>` с тегами `1.0.0`, `1.0` и
`latest`. Образ сам отдаёт и API, и собранный интерфейс, поэтому на сервере
достаточно одного контейнера.

Запуск опубликованного образа:

```bash
cp .env.example .env   # заполнить секреты и APP_BASE_URL
IMAGE=ghcr.io/<владелец>/<репозиторий> TAG=v1.0.0 \
  docker compose -f docker-compose.prod.yml up -d
```

Миграции накатываются автоматически перед стартом `api`. Интерфейс открывается
на порту 8000.
