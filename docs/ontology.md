# Доменная модель сервиса записи на встречи

Документ описывает предметную область словами и таблицами: какие сущности есть,
из чего они состоят, как связаны и какие правила обязаны выполняться всегда.

Это не описание кода. Код обязан соответствовать этому документу, а не наобороту.

## 1. Область одним абзацем

Эксперт описывает, на что можно записаться (**вид встречи**), и когда он
принимает (**расписание**). Из вида встречи и расписания получается сетка
**тайм-слотов** на конкретные даты. Гость выбирает слот и отправляет **заявку**,
которая занимает одно из мест в слоте. Собрав состав слота, эксперт **закрепляет**
его одним действием: слот закрывается для новых гостей, состав перестаёт
изменяться, создаётся приватная видеовстреча, и все участники получают письма со
ссылкой и паролем. Убранный, отозванный и не подтверждённый вовремя гость место
освобождает.

## 2. Сущности

### User, эксперт

Человек, который принимает заявки. Входит через Яндекс ID, пароля не имеет.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор, присваивает база |
| `yandex_id` | строка до 64 | да | Идентификатор аккаунта Яндекс ID, уникален |
| `login` | строка до 64 | да | Логин Яндекс ID, уникален |
| `email` | строка | да | Почта Яндекс ID, уникальна. Используется для писем эксперту |
| `display_name` | строка до 100 | да | Имя для показа в интерфейсе |
| `role` | `organizer` или `admin` | да | Права в панели |
| `timezone` | строка | да | Часовой пояс IANA, например `Asia/Krasnoyarsk` |
| `created_at` | дата и время | да | Момент первого входа, в UTC |
| `last_login_at` | дата и время | да | Момент последнего входа, в UTC |

Хранится в таблице `users`. Пароля и хеша пароля в таблице нет и быть не должно.

### Schedule, расписание

Правило, по которому строится сетка слотов. Принадлежит эксперту, а не виду
встречи: часы приёма заводятся один раз и используются всеми его видами встреч.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `owner_id` | целое | да | Эксперт, которому принадлежит расписание |
| `weekdays` | список чисел от 1 до 7 | да | Дни недели. 1 это понедельник, 7 это воскресенье |
| `start_time` | время | да | Начало рабочего окна, например `09:00:00` |
| `end_time` | время | да | Конец рабочего окна, например `18:00:00` |

Хранится в таблице `schedules`. Список дней недели лежит строкой вида
`"1,2,3,4,5"`, наружу отдаётся списком чисел.

### EventType, вид встречи

То, на что записывается гость. Отвечает на вопрос «что за встреча, сколько она
длится, сколько в ней мест и когда её надо подтверждать».

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `owner_id` | целое | да | Эксперт |
| `schedule_id` | целое | да | Расписание, по которому строятся слоты |
| `name` | строка до 100 | да | Название, например «Консультация по проекту» |
| `slug` | строка до 64 | да | Часть публичной ссылки. Уникален в паре с `owner_id` |
| `description` | строка до 500 | нет | Пояснение для гостя |
| `duration_minutes` | целое от 5 до 480 | да | Длительность встречи |
| `max_guests` | целое от 1 до 500 | да | Сколько гостей помещается в один слот. Значение 1 даёт обычную одиночную запись |
| `time_increment_minutes` | целое от 5 до 480 | да | Шаг сетки слотов |
| `min_notice_hours` | целое от 0 до 720 | да | За сколько часов минимум можно записаться |
| `horizon_days` | целое от 1 до 90 | да | На сколько дней вперёд открыта запись |
| `confirm_opens_hours` | целое от 0 до 168 | да | За сколько часов до начала слота открывается сбор состава |
| `confirm_deadline_hours` | целое от 0 до 168 | да | До какого момента до начала слота состав можно закрепить |
| `active` | да или нет | да | Открыт ли вид встречи для записи |
| `created_at`, `updated_at` | дата и время | да | Служебные моменты, в UTC |

Хранится в таблице `event_types`. Значение `max_guests`, равное 1, означает
встречу один на один, и никакого отдельного вида встречи для этого не требуется.

### Slot, тайм-слот

Конкретный промежуток времени на конкретную дату, который можно занять.
**В базе данных не хранится**, вычисляется при каждом запросе.

| Атрибут | Тип | Смысл |
|---|---|---|
| `event_type_id` | целое | Вид встречи |
| `date` | дата | День слота |
| `start_time` | время, UTC | Начало слота |
| `end_time` | время, UTC | Конец слота |
| `max_guests` | целое | Предел гостей, копируется из вида встречи для показа |
| `guest_count` | целое | Сколько заявок в статусах `pending` и `confirmed` |
| `remaining` | целое | Сколько мест осталось, не меньше нуля |
| `is_open` | да или нет | Слот ещё принимает заявки |
| `can_request` | да или нет | Можно ли сейчас отправить заявку на этот слот |

`is_open` истинен, пока закрепление слота не состоялось. `can_request` истинен,
когда слот открыт и `remaining` больше нуля.

### Session, сеанс

Запись о конкретном слоте, которая появляется в базе вместе с первой заявкой и
живёт до конца. Это единственное, что известно о слоте из базы: сам слот не
хранится.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `event_type_id` | целое | да | Вид встречи |
| `owner_id` | целое | да | Эксперт, копия для быстрых выборок |
| `date` | дата | да | День слота |
| `start_time` | время, UTC | да | Начало |
| `end_time` | время, UTC | да | Конец |
| `confirmed_at` | дата и время | нет | Момент закрепления состава. Пока пусто, слот открыт |
| `cancelled_at` | дата и время | нет | Момент отмены встречи |
| `conference_id` | строка до 128 | нет | Идентификатор встречи у провайдера |
| `join_url` | строка до 512 | нет | Ссылка на встречу |
| `meeting_password_enc` | двоичные данные | нет | Пароль встречи, зашифрован |
| `conference_status` | `not_created`, `pending`, `ready`, `failed` | да | Состояние создания встречи |
| `created_at` | дата и время | да | Момент появления, в UTC |

Хранится в таблице `sessions`. Уникальность на
`(event_type_id, date, start_time)` объявлена индексом.

Смысл `confirmed_at` двоякий и это сделано намеренно: он отвечает на два вопроса
сразу. Пока он пуст, слот открыт и принимает заявки. После того как он
проставлен, состав слота закрыт навсегда.

### Booking, заявка

Запись конкретного гостя на конкретный слот.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `event_type_id` | целое | да | Вид встречи |
| `owner_id` | целое | да | Эксперт, копия для быстрых выборок |
| `session_id` | целое | да | Сеанс, в состав которого входит заявка |
| `guest_name_enc` | двоичные данные | да | Имя гостя, зашифровано |
| `guest_email_enc` | двоичные данные | да | Почта гостя, зашифровано |
| `guest_email_bidx` | двоичные данные | да | Слепой индекс почты, по нему ищут |
| `guest_timezone` | строка | да | Часовой пояс гостя на момент заявки |
| `guest_note` | строка до 1000 | нет | Что гость хотел сказать |
| `status` | `pending`, `confirmed`, `removed`, `expired`, `cancelled` | да | Состояние заявки |
| `consent_version` | строка до 32 | да | Версия документа о обработке ПДн |
| `consent_at` | дата и время | да | Момент согласия, в UTC |
| `decided_at` | дата и время | нет | Момент закрепления, исключения или протухания |
| `decided_by` | целое | нет | Эксперт, принявший решение |
| `created_at`, `updated_at` | дата и время | да | Служебные моменты, в UTC |

Хранится в таблице `bookings`. Дата, время начала и конца хранятся в
`bookings` не дублируются из сеанса: при чтении они берутся присоединением, а в
таблице их нет. Имени и почты гостя в открытом виде в таблице нет.

### ConsentDocument, документ о обработке персональных данных

Версионируемый текст, с которым гость соглашается. Нужен, чтобы у заявки была
ссылка на конкретную редакцию документа, а не на «какой-то документ, который
когда-то был на сайте».

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `version` | строка до 32 | да | Версия, например `2026-10-01`. Уникальна |
| `title` | строка до 200 | да | Заголовок |
| `body_md` | строка | да | Текст документа |
| `effective_at` | дата и время | да | С какого момента действует, в UTC |

### OutboxEvent, событие рассылки

Запись, из которой фоновый воркер отправляет письмо. Существует, чтобы письмо
нельзя было потерять при сбое отправки. Подробности в
`docs/adr/0008-pisma-s-transactional-outbox.md`.

| Атрибут | Тип | Обязателен | Смысл |
|---|---|---|---|
| `id` | целое | да | Идентификатор |
| `kind` | строка до 40 | да | Повод письма |
| `booking_id` | целое | да | Заявка, из-за которой письмо |
| `to_email_enc` | двоичные данные | да | Адресат, зашифрован |
| `payload` | json | да | Данные письма: тема, текст, ссылка, пароль |
| `attempts` | целое | да | Сколько раз пытались отправить |
| `last_error` | строка до 500 | нет | Текст последней ошибки |
| `sent_at` | дата и время | нет | Момент успешной отправки |
| `created_at` | дата и время | да | Момент постановки в очередь |

## 3. Связи

| Связь | Кратность | Пояснение |
|---|---|---|
| User и Schedule | один ко многим | У эксперта несколько правил приёма |
| User и EventType | один ко многим | У эксперта несколько видов встреч |
| Schedule и EventType | один ко многим | Одни часы приёма используются несколькими видами встреч |
| EventType и Slot | один ко многим | Слоты вычисляются для конкретного вида встречи |
| EventType и Session | один ко многим | Одна запись о слоте на дату и время |
| Session и Booking | один ко многим | Главная связь предметной области: в слот входит много гостей |
| Booking и OutboxEvent | один ко многим | По заявке может уйти несколько писем |
| ConsentDocument и Booking | один ко многим | Заявка ссылается на версию документа |

```
User 1 ------ * Schedule
 |                 |
 |                 v
 * ------------> EventType
                     |
      вычисляется    |    хранится
        -------------+--------------
        v                           v
      Slot  <---- отвечает ----  Session 1 ---- * Booking ---> OutboxEvent
  (не хранится)                     (встреча)      (заявка)      (письмо)
```

Слот и сеанс описывают одно и то же время с двух сторон: слот это то, что
вычисляется для показа гостю, сеанс это то, что известно базе о занятом времени.

Удаление вида встречи удаляет его сеансы и заявки (`ON DELETE CASCADE`).

## 4. Инварианты

Правила, которые обязаны выполняться всегда. Каждое проверено тестами.

| № | Инвариант | Где проверяется |
|---|---|---|
| И1 | На один слот не более `max_guests` заявок в статусах `pending` и `confirmed` | Подсчёт под блокировкой строки сеанса, `docs/adr/0004` |
| И2 | `max_guests` вида встречи от 1 до 500 | Схема вида встречи |
| И3 | `start_time` расписания строго раньше `end_time` | Проверка при создании и правке расписания |
| И4 | Слот целиком помещается в рабочее окно расписания | Условие цикла в движке слотов |
| И5 | `end_time` слота равен `start_time` плюс `duration_minutes` | Функция расчёта слотов |
| И6 | Заявка возможна только на время, которое есть в сетке слотов | Поиск слота перед созданием заявки |
| И7 | Слот не ближе `min_notice_hours` и не дальше `horizon_days` от момента запроса | Проверка при расчёте сетки и перед созданием заявки |
| И8 | Закрепить состав можно только в окне от `start_time` минус `confirm_opens_hours` до `start_time` минус `confirm_deadline_hours` | Проверка в обработчике закрепления |
| И9 | `confirm_opens_hours` не меньше `confirm_deadline_hours`, иначе окно пустое | Схема вида встречи |
| И10 | Закрепление состава переводит в `confirmed` все заявки в статусе `pending` этого сеанса | Транзакция закрепления |
| И11 | После `confirmed_at` состав сеанса не меняется: ни одну заявку нельзя добавить или убрать | Проверки в обработчиках заявок и закрепления |
| И12 | Заявка в статусе `removed`, `expired` или `cancelled` место не занимает | Условие в подсчёте и в частичном индексе |
| И13 | Встреча не создаётся, если после закрепления в слоте нет ни одной заявки в статусе `confirmed` | Проверка перед вызовом провайдера |
| И14 | Пароль и ссылка показываются гостю только у сеанса со статусом `ready` | Сборка ответа гостю |
| И15 | Один гость не может иметь две заявки на один слот | Частичный уникальный индекс, `docs/adr/0004` |
| И16 | Гостя находят по `guest_email_bidx`, открытое значение почты в базе отсутствует | `docs/adr/0005` |
| И17 | У заявки заполнены `consent_version` и `consent_at` | Схема заявки |
| И18 | Заявку нельзя исключить или отозвать повторно, если она уже не в статусе `pending` | Проверка в обработчиках |
| И19 | Отозванная заявка не удаляется, а переводится в `cancelled` | Условие в обработчике отмены |
| И20 | Диапазон дат запроса слотов не длиннее 60 дней | Проверка в обработчике слотов |

## 5. Жизненный цикл сеанса

```
    первая заявка            закрепление состава
   ---------------> открыт ---------------> закрыт
                        |                      |
                        | протухание          | отмена встречи
                    не подтверждён           v
                        |                 отменён
                        v
                    не состоялся
```

У сеанса три состояния в базе, а не пять: его состояние выражается наличием
`confirmed_at` и `cancelled_at`.

Пока `confirmed_at` пусто, слот открыт. После закрепления состав закрыт навсегда
и встреча создаётся. Если вовремя не подтвердили, заявки протухают и место
освобождается, а сеанс остаётся открытым и пустым.

## 6. Жизненный цикл заявки

```
        создание            закрепление состава
  --------------------> pending -------------> confirmed
                            |                       |
  исключение, отзыв,        |                       | отзыв гостя
  протухание                v                       v
                     removed  expired            cancelled
```

Переходы из `pending` терминальные и необратимые: исключил, отозвал или
протухла, вернуть в строй можно только новой заявкой. Из `confirmed` возможен
только отзыв гостя. Других переходов нет.

## 7. Правило закрытости состава

Главное правило продукта: **состав закреплённого слота неизменен**.

Закрепление это единственное действие, которое переводит слот из открытого в
закрытый, и оно же создаёт встречу и рассылает письма. Письмо отозвать нельзя, а
пароль встречи один на весь состав, поэтому изменить состав после отправки писем
означало бы оставить кого-то впустую или впустить без ведома. Поэтому:

- убрать гостя можно только пока слот открыт, заявка в статусе `pending`;
- добавить гостя можно только пока слот открыт;
- если после исключения гостей в слоте не осталось никого, встреча не создаётся
  вовсе, а слот закрывается и гостям уходит письмо, что время не подошло.

## 8. Поводы писем

| Повод | Кому | Когда |
|---|---|---|
| `request_received` | эксперту | Создана заявка |
| `booking_confirmed` | каждому участнику | Состав закреплён, в письме ссылка и пароль |
| `booking_removed` | гостю | Эксперт убрал его из состава |
| `booking_expired` | гостю | Состав не закрепили до дедлайна |
| `session_cancelled` | всем участникам | Эксперт отменил встречу |

Формулировки писем говорят о заявке, а не о встрече, кроме случая отмены
встречи. Иначе письмо об исключении вводит гостя в заблуждение, когда встреча
из-за него спокойно состоится.

## 9. Словарь терминов

| Термин | Значение в этом проекте |
|---|---|
| Эксперт | Тот, кто принимает заявки. Входит через Яндекс ID |
| Гость | Тот, кто записывается. Учётной записи нет, опознаётся по почте |
| Вид встречи | То, на что записываются: консультация, код-ревью, групповой разбор |
| Расписание | Правило «дни недели плюс рабочее окно» |
| Рабочее окно | Промежуток от `start_time` до `end_time` внутри одного дня |
| Шаг сетки | Через сколько минут начинается следующий слот |
| Тайм-слот | Конкретный промежуток на конкретную дату |
| Предел гостей | Сколько заявок помещается в один слот. Один это одиночная запись |
| Заявка | Запись гостя на слот, ждущая закрепления |
| Сеанс | Хранимая запись о занятом слоте и о связанной с ним встрече |
| Закрепление | Действие эксперта, закрывающее состав слота и создающее встречу |
| Окно закрепления | Интервал между началом сбора состава и дедлайном |
| Пароль встречи | Общий для состава пароль, письмом отправляется участникам |
| Слепой индекс | Хеш нормализованной почты, по которому ищут заявки гостя |
