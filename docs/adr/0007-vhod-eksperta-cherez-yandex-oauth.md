# ADR 0007. Вход эксперта через OAuth Яндекс ID

- **Статус:** принято
- **Дата:** 5 октября 2026
- **Авторы:** команда проекта

## Контекст

Требование задачи: «вход по SSO». Гость при этом регистрацией не занимается по
продуктовому решению, а эксперту нужна панель.

«SSO» в требовании означает, что эксперт не заводит пароль в нашем сервисе, а
показывает учётную запись, которой уже пользуется. Свой пароль у сервиса не
должен быть вовсе: значит нет ни формы пароля, ни хеша пароля, ни его соли, ни
темы восстановления доступа.

Отдельно важно, что доступ к Телемосту и вход эксперта авторизуются **одним и тем же
аккаунтом Яндекс ID**, но **разными OAuth-приложениями**, потому что у Яндекса два
типа приложений с разными ограничениями.

| Тип приложения | Где создаётся | Redirect URI | Для чего |
|---|---|---|---|
| Для авторизации пользователей | `oauth.yandex.ru/client/new/id/` | редактируется, можно несколько | вход эксперта, чтение профиля |
| Для доступа к API | `oauth.yandex.ru/client/new/` | не меняется, фиксирован `https://oauth.yandex.ru/verification_code` | сервисные API, в том числе Телемост |

Поэтому в конфигурации два ClientID. Подробности получения токена Телемоста в
ADR 0009.

## Рассмотренные варианты

**Собственные пароли.** Отклонено: противоречит требованию, и появляется
обязанность хранить хеши и защищать их.

**ОткрытыйID Коннект через внешнего провайдера, например university SSO или
Keycloak.** Технически правильнее для организации, но требует согласования с
администрацией, регистрации клиента во внешней системе и времени на
согласование. Отклонено как неподъёмное для задачи.

**Яндекс OAuth, полный цикл на бэкенде.** Выбрано.

**Яндекс OAuth с готовой кнопкой «Войти через Яндекс», конфигурация только на
бэкенде.** Выбрано как основной сценарий.

## Решение

Регистрируем OAuth-приложение типа «Для авторизации пользователей» на
`oauth.yandex.ru/client/new/id/`. Оно запрашивает права `login:email login:info`.

Вход реализован как `redirect_uri` на бэкенд, это вариант «мгновенная авторизация»
из документации Яндекс ID. Обработчик проверяет `state`, меняет код на токен
запросом `POST https://oauth.yandex.ru/token` с `grant_type=authorization_code`,
читает профиль вызовом `GET https://login.yandex.ru/info?format=json`, находит
или создаёт пользователя по `yandex_id` и кладёт в сессию.

Токен Яндекс ID передаётся в заголовке `Authorization: OAuth <токен>`. Имя схемы
именно `OAuth`, а не `Bearer`: это особенность Яндекса, и её легко написать не
так, получив `401` на ровном месте.

Токен Яндекс ID сам по себе не является сессией в нашем сервисе: он живёт в
своей таблице `oauth_tokens` и нужен для вызовов Телемоста, потому что у него
короткий срок жизни. Идентификатор сессии нашего сервиса подписан, чтобы
подделать его было нельзя, и хранится в защищённой cookie `HttpOnly`.

Разделение на роли: `admin` видит панель целиком, `organizer` только свои
события и заявки. Роль назначается вручную администратором, из интерфейса не
меняется.

Если первый вошедший пользователь ещё не существует, он автоматически
получает роль `organizer` и пустую панель. Это избавляет от отдельной страницы
первичной настройки, но означает, что любой, кто вошёл через Яндекс, получает
доступ к панели. В ADR зафиксировано как осознанное допущение, закрыть его
можно строкой `ALLOWED_LOGINS` в конфигурации, которая проверяется при входе.

Гость не авторизуется вообще. Его «вход» это ввод почты на странице своих
броней.

## Последствия

**Положительные:**

- Паролей в сервисе нет вообще, поэтому нет и целого класса задач: хранение
  хешей, соль, восстановление, защита от подбора.
- Логин, имя и почта эксперта приходят от Яндекса, вводить их руками не нужно.
- Один аккаунт Яндекс ID обслуживает и вход, и доступ к Телемосту, хотя
  приложения у них два, см. ADR 0009.
- Внешний провайдер отвечает за двухфакторную аутентификацию сам.

**Отрицательные:**

- Нужен интернет и доступность Яндекса. Если он недоступен, не войдут даже те,
  у кого аккаунт есть.
- Приложение Яндекса проходит модерацию, и его ClientID и Secret становятся
  его публичными. Их нельзя считать секретом приложения.
- Пока приложение не верифицировано, пользователь видит предупреждение перед
  выдачей доступа, и часть людей на этом шаге отваливается. Для боя верификация
  обязательна.
- Вход возможен только на русскоязычную почту Яндекса, эксперт с другой почтой
  не войдёт. Для проекта это ограничение приемлемо.
- Токен Яндекса хранится у нас, значит его нужно защищать и уметь обновлять, а
  вместе с этим нужна таблица и логика обновления.
- Права `login:email` запрашивают у пользователя согласие, поэтому экран входа
  Яндекса показывает, что приложение запрашивает доступ к почте. Это верно, но
  стоит предупредить эксперта заранее.
