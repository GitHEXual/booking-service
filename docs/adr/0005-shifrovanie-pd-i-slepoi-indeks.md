# ADR 0005. Персональные данные: шифрование колонок и слепой индекс

- **Статус:** принято
- **Дата:** 5 октября 2026
- **Авторы:** команда проекта

## Контекст

Сервис собирает персональные данные гостя: имя, адрес почты, иногда телефон.
Требование задачи: «шифрование данных в базе». Требование из раздела
«Должно быть»: дисклеймер и документ об обработке персональных данных.

Что именно значит «шифрование в базе», надо определить, потому что есть два
разных требования, и их часто путают:

- **Шифрование носителя.** Файл базы или бэкап защищён целиком. Реализуется
  шифрованием тома или встроенным шифрованием в СУБД.
- **Шифрование данных о ПДн.** Значения полей недоступны тому, кто получил файл
  базы или бэкап, но не имеет ключа.

Для сервиса записи реальная угроза выглядит так: кто-то получает копию базы
или резервную копию и читает имена и почты людей, которые записались на
консультацию. Это и есть тот случай, который нужно закрывать. Шифрование тома
закрывает его только пока том смонтирован и ключ доступен, а при выгрузке
дампа на стороне бэкап-хранилища защита зависит от настроек этого хранилища.

Дополнительное условие, которое ломает наивное решение: сценарий «гость
находит свои брони по адресу почты без регистрации» есть в продукте. То есть по
зашифрованной почте нужно искать.

## Рассмотренные варианты

**Шифрование тома или файла базы (LUKS, SQLCipher, pg_tde).** Закрывает угрозу
«файл базы попал к постороннему». Отклонено как единственная мера: приложение
должно видеть открытые значения, чтобы работать, а требование звучит про
защиту данных о ПДн, а не про защиту носителя. В PostgreSQL встроенного
шифрования таблиц в открытой версии нет, `pg_tde` есть только у отдельных
поставщиков.

**Шифрование колонок средствами PostgreSQL, `pgcrypto`.** Работает, ключ задаётся
на сессию. Отклонено: чтобы база шифровала и расшифровывала, ключ должен
передаваться в сессию, и при дампе из живой сессии данные выходят открытыми.
Ключ также оказывается в одном контуре с данными.

**Шифрование колонок в приложении, AES-256-GCM.** Выбрано. Приложение
шифрует и расшифровывает само, ключ живёт только в переменных окружения, база
никогда не видит открытых значений.

**Одноключевое шифрование с детерминированным режимом, чтобы искать по
шифротексту.** Отклонено: равенство шифротекстов раскрывает, у каких гостей
почта совпадает, и это утечка поверх AES.

## Решение

Шифруем значения на уровне приложения алгоритмом AES-256-GCM. Ключ берётся из
переменной окружения `PII_ENCRYPTION_KEY`, в базе не хранится и в логах не
печатается. Оформляется как `TypeDecorator` в SQLAlchemy, поэтому в доменном
коде остаются обычные строки.

Имя гостя шифруется в `guest_name_enc`, почта в `guest_email_enc`.

**Слепой индекс.** Чтобы найти заявки по почте, рядом лежит
`guest_email_bidx` это `HMAC-SHA256` от нормализованной почты под отдельным
ключом `PII_LOOKUP_KEY`. Поиск идёт по индексу, он детерминированный, а
используется другой ключ, поэтому равенство индексов не раскрывает содержимое.

Нормализация обязательна и делается до шифрования и до хеширования: обрезка
пробелов и приведение к нижнему регистру. Без неё `Иван@Mail.ru` и
`иван@mail.ru` не найдут друг друга, а это один и тот же человек.

Телефон гостя, если появится, шифруется так же, а поиска по нему не делается,
поэтому слепой индекс для него не нужен.

Факт согласия хранится открытым текстом, потому что он не разоблачает гостя:
`consent_version` и `consent_at`. Ссылаются они на запись в таблице
`consent_documents` с конкретной версией документа.

## Последствия

**Положительные:**

- Слив базы или бэкапа не раскрывает ни одного имени и ни одной почты гостя без
  ключа из окружения.
- Ключ и данные лежат в разных контурах: база физически отдельно, ключ в
  переменных окружения или в менеджере секретов.
- Два ключа выполняют разные задачи, поэтому компрометация одного не даёт
  возможности ни читать значения, ни искать по ним.
- Шифрование оформлено как тип колонки, поэтому не протекает в остальной код:
  обработчики работают со строками.
- Функции шифрования и нормализации чистые и тестируются без базы, в том же
  стиле, что и движок слотов.

**Отрицательные:**

- Поиск по почте идёт только по точному совпадению. Сортировка, поиск по
  подстроке и `LIKE` по ПДн невозможны без расшифровки всех строк, поэтому
  такие возможности в проекте запрещены.
- Индекс не даёт уникальности сам по себе, её даёт отдельный уникальный индекс
  по `guest_email_bidx`, это в ADR 0004.
- Ключи нельзя менять без миграции всех строк. Процедуру ротации ключа нужно
  описать отдельно, в этой версии она не автоматизирована.
- Отлаживать данные в базе удобнее не станет: в выгрузке вместо почты будет
  шифротекст. Это осознанная цена.
