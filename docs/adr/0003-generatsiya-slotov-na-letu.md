# ADR 0003. Тайм-слоты вычисляются на лету, а не хранятся в базе

- **Статус:** принято
- **Дата:** 7 октября 2026

## Контекст

Расписание это недельное правило: дни недели и рабочее окно, например с 09:00 до
18:00. Вместе с длительностью и шагом вида встречи оно даёт конкретные слоты на
конкретные даты. Своих данных у слота нет: всё выводится из правила.

## Решение

Слоты не хранятся. `backend/slots.py` собирает сетку чистыми функциями
(`build_slots`, `find_slot`) по объекту `Правило`. В базу эти функции не ходят:
обработчик сам достаёт занятое время и передаёт его в правило.

Занятость это начала слотов, на которые есть заявка в статусе `pending` или
`confirmed`, плюс закрытые сеансы. Всё время в сетке отдаётся в UTC, переводит
для показа интерфейс (ADR 0010).

В базе остаётся только `Session`: запись о занятом слоте, которая появляется с
первой заявкой. Уникальность держит индекс `(event_type_id, start_at)`.

## Последствия

- **Плюс:** нет задачи синхронизации: правка расписания не требует чинить старые
  слоты, которых нет.
- **Плюс:** логика покрывается тестами на обычных объектах, без базы.
- **Минус:** сетка пересчитывается на каждый запрос; при большом горизонте это
  заметная работа, для нашего объёма приемлемо.
- **Минус:** слот нельзя назвать идентификатором, поэтому есть отдельная проверка
  `find_slot`, что запрошенное время действительно есть в сетке.
