# ADR 0011. Контракт API: снимок OpenAPI в репозитории и тест на дрейф

- **Статус:** принято
- **Дата:** 5 октября 2026
- **Авторы:** команда проекта

## Контекст

Эталонный проект `booking-reference` собран методом Design First. Источник истины
это `contract/main.tsp` на TypeSpec, из него компилятор собирает
`contract/openapi.yaml`, а тест `contract.test.ts` требует, чтобы приложение этому
контракту подчинялось: набор эндпоинтов, коды состояний и тела ответов должны
совпадать. Непрерывная интеграция пересобирает контракт и сравнивает результат с
закоммиченным файлом, поэтому забытый пересбор валит сборку.

Мы выбрали другой стек, Python и FastAPI. TypeSpec здесь не подходит, но
**проверяемость контракта** из эталонного проекта бросать не хочется: без неё
описание API разъезжается с кодом незаметно, и это ровно тот класс дефектов,
который не ловится типами.

Рассмотренные варианты:

- **Писать `openapi.yaml` руками, код приводить к нему.** Отклонено: это второй
  язык описания данных рядом с Python, и рассинхронизация вопрос времени, а не
  «если».
- **Не заводить контракт вообще, полагаться на автодокументацию FastAPI.**
  Отклонено: автодокументация описывает то, что уже написано, поэтому она
  расходится с замыслом раньше, чем его нарушение заметят.
- **Снимок сгенерированного контракта в репозитории плюс тест на дрейф.**
  Выбрано.

## Решение

FastAPI генерирует OpenAPI сам из аннотаций. Мы зафиксировали порядок, в котором
это работает, чтобы контракт оставался проверяемым артефактом, а не
побочным эффектом:

1. `npm`-аналог команды `make contract` в проекте отсутствует, вместо этого
   есть скрипт `python -m app.export_openapi`, который выгружает
   `app.openapi()` в `docs/openapi.json` и вставляет файл в репозиторий.
2. Тест `tests/test_openapi_contract.py` сравнивает `app.openapi()` с
   содержимым `docs/openapi.json` и падает при расхождении, печатая разницу.
3. Непрерывная интеграция запускает тот же тест. Значит изменить API, забыв
   пересобрать снимок, нельзя.
4. Дополнительно тест проходит по `docs/openapi.json` и проверяет, что в нём
   есть все операции, перечисленные в PDR, и что у каждой объявленной ошибки
   есть тело ответа. Это возвращает эталонную гарантию, что каждый код ошибки
   хотя бы раз объявлен и покрыт.

Единая схема ошибки описана один раз в модуле ошибок и используется во всех
обработчиках, поэтому тело любой ошибки одинаково: машиночитаемый код и текст для
пользователя.

## Последствия

**Положительные:**

- Изменение контракта без пересборки снимка ломает сборку, а не остаётся
  незамеченным.
- Нет второго языка описания данных, который надо поддерживать в актуальном
  состоянии.
- Документация API всегда присутствует в репозитории и читается без запуска
  приложения.
- Появляется проверка, что каждый объявленный повод ошибки реально может
  возникнуть.

**Отрицательные:**

- Появляется файл, который надо пересобирать руками при изменении аннотаций.
  Это та же цена, что и в эталонном проекте с TypeSpec, просто дешевле.
- Момент появления изменения в контракте сдвигается: теперь контракт
  фиксирует то, что уже написано в коде, а не то, что задумано. Порядок
  «сначала контракт, потом код» сохраняется на уровне намерения и ревью, но не
  на уровне компиляции.
- Снимок может разойтись с `Pydantic`-схемами внутри приложения, потому что
  FastAPI строит контракт из них: если схема меняется для внутреннего
  использования, меняется и контракт, и это нужно отслеживать.
